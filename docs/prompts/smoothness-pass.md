# Промпт: проход по плавности интерфейса

Запуск: «работай по `docs/prompts/smoothness-pass.md`» (можно с уточнением: «только фаза 2», «только телефоны», «только сцена 06»).

## Цель

Главная страница `/` летает: скролл не рвётся, пины и переходы не подёргиваются, WebGL-сцены не роняют кадры, ничего не «думает» на первом экране. Цель по кадру: 60 fps на среднем ноутбуке (бюджет кадра 16,7 мс, из них наш JS не больше ~6 мс), на телефоне среднего класса не ниже 45 fps. Всё, что выглядит и работает так же, но дешевле, делаем. Всё, что делает сайт беднее, не делаем.

## Нерушимые рамки

Это решения владельца, оптимизация их не пересматривает (подробности в `AGENTS.md`):

- Ни одна фича не вырезается и не упрощается ради fps: телефоны получают всё то же, что десктоп (пины сцен, WebGL, станции маскота, шина); три транзита, hero-остров, 03-слэб, футер с выключением остаются.
- Маскот после интро всегда на экране (кроме «за контентом секции»), без телепортов. Оптимизировать можно его рендер, нельзя прятать.
- Lenis владеет скроллом, GSAP/ScrollTrigger владеет пинами и скрабами. Новых анимационных библиотек нет. Никаких React-стейтов на кадр скролла. Один авторитетный таймлайн на сцену.
- Пин-тяжёлые и брейкпоинт-зависимые таймлайны только через `gsap.matchMedia`. Переход через 761px пересобирает всё.
- `prefers-reduced-motion`: весь контент читается.
- Токены в единственном `:root`. Когда заменяешь секцию, удаляй её CSS в том же изменении.
- Внешний вид и ощущение движения не меняются: оптимизация должна быть невидимой. Если тонкость пейсинга (`lib/motion/pace.ts`, длины сцен) страдает, это отдельный разговор с владельцем, а не побочный эффект.

## Порядок работы: сначала измерить, потом чинить

Не оптимизируй на глаз и «по привычке». Каждое изменение должно опираться на цифру до и после. Если цифры не изменились, изменение откатывается.

### Фаза 0. Рабочая среда

- Dev-сервер пользователя на 3100 не трогать и не перезапускать без нужды. `npm run build` в самом проекте запрещён (перетрёт его `.next`): сборку проверять в копии в scratchpad, с полным длинным путём и отдельным вызовом с проверкой cwd (см. память `dev-server-port-3100`).
- Встроенная Browser pane рисует кадры только на скриншотах, её fps ничего не значит (память `browser-pane-frames`). Замеры только в headless Chrome через puppeteer-core в scratchpad.
- Замерять на **production-сборке** (копия + `next start` на отдельном порту), а не на `next dev`: dev-режим с HMR, StrictMode-двойными эффектами и несжатым кодом даёт ложные цифры.
- Для GL сначала попробовать реальный GPU (`--use-angle=d3d11` / `--enable-gpu`), `--use-angle=swiftshader` как запасной. Swiftshader считает на CPU, его абсолютные мс не годятся, только относительное сравнение «до/после» и число draw call / контекстов / пикселей.
- Профиль: CDP `Performance.getMetrics`, `Tracing` (категории `devtools.timeline`, `disabled-by-default-devtools.timeline.frame`, `gpu`), Long Tasks / `PerformanceObserver`, замер кадра через `requestAnimationFrame` дельты во время автоскролла.
- Размеры вьюпорта по `AGENTS.md`: 1440×900, 1280×800, 768×1024, 390×844. Телефон эмулировать с `deviceScaleFactor: 3` и CPU throttling 4× (`Emulation.setCPUThrottlingRate`), это и есть настоящий худший случай.

### Фаза 1. Базовые замеры (ничего не менять)

Написать один повторяемый скрипт `qa/perf/scroll-run.js` (и положить рядом `README` на пять строк), который:

1. Открывает страницу, ждёт конца прелоадера/интро.
2. Прокручивает всю страницу (~27 экранов) ровным темпом, как колесо, через Lenis (`wheel`-события), а не `scrollTo`, потому что нужен реальный путь Lenis → ScrollTrigger → сцены.
3. На каждый экран пишет: p50/p95/p99 длительности кадра, число кадров дольше 16,7/33 мс, long tasks (>50 мс), время Style/Layout/Paint/Composite, JS самого ticker'а, количество активных WebGL-контекстов, `drawArrays/drawElements` за кадр на каждый из них, размер drawing buffer каждого канваса.
4. Выдаёт таблицу «сцена/экран → метрики» в JSON и в читаемый вид. Сохранять в `qa/perf/results/<дата>-<метка>.json`.

Плюс отдельно: загрузка (LCP, TBT, размер JS и media на первом экране, время до интерактива интро), память (рост heap за полный проход; утечки при пересборке через 761px, при повторных заходах в сцену), нагрев/батарея не меряем, но следим за числом работающих циклов, пока их никто не видит.

Результат фазы: список «худших мест» с цифрами. Дальше работаем сверху вниз по этому списку.

### Фаза 2. Что искать (проверять каждый пункт, но чинить только то, что подтвердилось замером)

**Рендер-циклы и контексты WebGL** (самое вероятное узкое место: сейчас ≥5 независимых GL-контекстов: маскот, три транзита через один рендерер, hero-остров, 03-слэб, футер/SignalField, плюс `ModuleModels` на 2D)
- Каждый цикл рисует только когда его сцена на экране или нужна (IntersectionObserver / состояние ScrollTrigger). Проверить, что ни один `gsap.ticker.add(tick)` не крутит рендер невидимой сцены: `Mascot.tsx`, `TransitScene.tsx`, `HeroIsland.tsx`, `ShowcaseScene.tsx`, `StackBoard.tsx`, `ModuleModels.tsx`, `SignalFieldCanvas.tsx`, `PixelMark.tsx`, `live.ts`, `AlphaVideo.tsx`.
- Не рисовать кадр, если ничего не изменилось (dirty flag), особенно в простое маскота и в статичных остановках сцен.
- Мёртвый код: `ModuleModels` / `lib/modules` на портфолио не рендерятся; убедиться, что их чанк не грузится.
- Число контекстов одновременно: браузеры сбрасывают старые при >8–16, на телефонах меньше. Считать живые контексты на каждом экране.

**Пиксельная нагрузка**
- DPR: единый потолок (сейчас разные: `SignalFieldCanvas` 1,75, `ShowcaseScene` 2, остальные проверить). На телефоне с DPR 3 буфер не больше ~1,5–2×, но визуально пиксельный стиль сайта это не должно задевать, так что сверять скриншотами до/после.
- Размер канвасов: полноэкранные fixed-канвасы (маскот, транзит) дороже всего; рассмотреть внутренний масштаб (рисовать в меньшем буфере и апскейлить), если стиль «битмап» позволяет без видимой потери.
- `antialias: true` у showcase-рендерера, MSAA на больших буферах, прозрачность и premultiplied alpha на полноэкранных слоях: проверить цену.
- Адаптивное качество: простой скользящий замер длительности кадра в самом рендерере; при устойчивом провале (p95 > 24 мс несколько секунд) понижать DPR / число воксельных деталей на шаг, при запасе вернуть. Без React-стейта, внутри цикла.

**Скролл и пины**
- `ScrollTrigger.refresh()` не чаще необходимого; на ресайз дебаунс; нет ли layout thrashing (чтение `getBoundingClientRect`/`offsetHeight` вперемешку с записью стилей внутри `onUpdate`).
- В `onUpdate` скрабов: нет аллокаций (новые объекты/массивы на кадр), нет `querySelectorAll`, нет чтения layout. Кэшировать узлы и размеры, обновлять их по `refresh`.
- Связка Lenis ↔ GSAP: один тикер, `lagSmoothing(0)` оставлен осознанно (проверить, что не создаёт скачков после вкладки в фоне).
- `pace()` и фолловеры: вычисления только пока сцена активна.
- `SectionRail` и `SignalBus`: rAF/обновления по скроллу не должны делать layout; шина и рейл не перерисовывают SVG целиком на кадр.

**CSS и композитинг**
- `app/globals.css` 4610 строк: найти мёртвые правила (секции, которые заменены; `styles/legacy-routes.css` для dormant-маршрутов не должен грузиться на `/`), дорогие селекторы.
- Анимировать только `transform`/`opacity`/`clip-path` на собственных слоях; убрать анимации `top/left/width/height/box-shadow/filter` в скролл-путях. `will-change` ставить точечно и снимать после сцены, не на десятках элементов (каждый такой слой стоит видеопамяти, особенно на телефоне).
- `backdrop-filter`, большие `filter: blur`, `mix-blend-mode`, крупные `box-shadow` на движущихся/больших слоях: измерить и заменить на запечённые варианты, если дорого.
- CSS 3D сцены (02 колода, 03 кольцо, 04 стек, 05 вьюер): число слоёв и их размер; `contain: layout paint` / `content-visibility: auto` на секциях вне пина; `backface-visibility`, ненужные `preserve-3d` вложения.
- Шрифты: `font-display`, subset, preload только того, что на первом экране.

**Загрузка и память**
- Размер стартового JS (анализ бандла: `@next/bundle-analyzer` в копии, не в проекте как зависимость без согласования), динамические импорты для тяжёлого, что не нужно до интро (рендереры сцен ниже первого экрана грузить заранее, но без блокировки главного потока: `requestIdleCallback`).
- Постеры/видео: форматы (AVIF/WebP, VP9/H.264 с альфой), размеры под реальный размер показа, `preload="none"` вне экрана, `decoding="async"`, `loading="lazy"`; видео не декодируется вне экрана (`AlphaVideo` уже на IO, проверить).
- Текстуры/буферы WebGL: освобождаются ли при уходе сцены, нет ли повторной генерации текстур (капчуры, `live.ts` с `willReadFrequently` канвасом) на каждый кадр.
- Утечки: слушатели, observer'ы, тикеры, GL-ресурсы при размонтировании, StrictMode и пересборке через 761px.

**Главный поток**
- Тяжёлая инициализация (сборка мешей транзитов, модель маскота `hd.ts`/`model.ts`, раскладка стека) не одним куском на старте: разбить по idle-слайсам или вынести в Worker/OffscreenCanvas только если выигрыш подтверждён и это не ломает архитектуру (на это нужно согласие владельца, если меняется владение рендером).
- События `scroll`/`resize`/`pointermove`: пассивные слушатели, один общий вместо россыпи.

### Фаза 3. Правки

- Один приём за раз, мелкими коммитами, каждый с замером «до → после» в сообщении коммита (по метрикам из фазы 1).
- Порядок: сначала то, что даёт больше всего при меньшем риске (остановка невидимых циклов, dirty flag, DPR-потолок, мёртвый CSS/JS), потом структурное.
- После каждого приёма: `npm run typecheck`; визуальная сверка до/после (headless-скриншоты, те же кадры и viewport'ы); проверка, что reduced motion и пересборка через 761px не сломались.
- Если приём требует решения про внешний вид, фичу или архитектуру (Worker, снижение разрешения слоя, замена эффекта), остановиться и спросить владельца, показав цифры и скриншоты вариантов.

### Фаза 4. Приёмка

Итоговая таблица «было/стало» по тем же сценариям на 1440×900, 1280×800, 768×1024 и 390×844 (с троттлингом CPU 4×). Критерии:

- p95 кадра при полном проходе ≤ 16,7 мс десктоп, ≤ 22 мс телефон с троттлингом; кадров > 33 мс почти нет (<1%);
- ни одного long task > 100 мс после интро;
- одновременно не более 3 работающих GL-циклов, остальные спят;
- heap после трёх полных проходов и пересборки через 761px не растёт;
- LCP и TBT не хуже базовых, стартовый JS не больше базового;
- визуально идентично: те же скриншоты сцен в тех же позициях скролла.

Закончить: `npm run typecheck`, сборка в копии, краткий отчёт владельцу на русском (что нашли, что починили, цифры, что осталось и что требует его решения). Если за проход вскрылось неочевидное правило (например, «этот эффект дорог, трогать только так»), записать его в память проекта и, если оно архитектурное, в `AGENTS.md`.

## Чего не делать

- Не оптимизировать вслепую и не менять то, что не вошло в «худшие места».
- Не снижать количество сцен, вокселей, частиц или длины сцен ради цифр без согласия.
- Не мерять в Browser pane и не мерять `next dev`.
- Не билдить в проекте; не перезапускать dev-сервер на 3100 без причины.
- Не добавлять зависимости (профайлеры, бандл-анализаторы) в `package.json` проекта.
- Не заявлять «стало плавнее» без таблицы до/после.
